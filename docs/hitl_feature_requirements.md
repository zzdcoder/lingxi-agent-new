## 1. 文档说明

### 1.1 背景

lingxi-agent 是基于 LangGraph 的智能问答平台，服务两类用户：

- **移动客户（外部）**：通过知识库问答解决业务咨询，答案质量直接代表企业形象；
- **厂商内部（我们）**：借助平台检索开发文档、加速开发，知识库内容由我们自行生产与维护。

平台已具备 **数据库写操作审批** 的 HITL 能力（update/delete 触发 → 前台审批卡片 → 决策接口恢复），验证了「中断 → 人工决策 → 恢复」全链路的可行性。本文档在此基础上，围绕两类用户的真实业务痛点，挖掘 **3 个合理、可落地的人工介入（HITL）需求**，让人的判断力作用于价值密度最高的环节。

### 1.2 目标与范围

- 挖掘并描述 3 个 HITL 功能需求，给出业务价值、触发条件、交互流程、状态机与验收标准；
- 全部需求**复用现有 HITL 框架**（approval_request 表、SSE 审批卡片、决策接口、检查点恢复），不引入新的中断原语；
- 本文档为需求评审稿，**评审通过后**再合并进入 `lingxi_agent_langgraph_redesign.md` 实施。

### 1.3 术语

| 术语      | 说明                                      |
| ------- | --------------------------------------- |
| HITL    | Human-in-the-loop，人工介入闭环                |
| 审批卡片    | 前端对话窗口中渲染的交互式卡片（六区块：头部/明细/上下文/操作/回显/提示） |
| 审核人/复核人 | 具备相应权限的后台用户（JWT 身份）                     |
| 知识库文档   | 上传并向量化入库、供检索的文档                         |

## 2. 现状与痛点分析

### 2.1 现状能力

| 能力         | 说明                                                |
| ---------- | ------------------------------------------------- |
| 写操作审批 HITL | LLM 决策 update/delete 时中断，前台卡片审批通过后恢复执行            |
| 意图路由       | knowledge_base / task / chat 多标签分类，低置信度降级         |
| 文档入库       | 上传 → 清洗分块 → 预览 → 可选向量化 + 语义缓存失效，一次性完成             |
| 权限模型       | 知识库文档 auth_option ∈ {public / private-本人}，检索按用户过滤 |

### 2.2 痛点（需求来源）

| 痛点                    | 关联用户 | 说明                                        |
| --------------------- | ---- | ----------------------------------------- |
| P1：入库无人把关，脏数据直接污染线上答案 | 厂商   | 文档入库全自动，乱码、重复、内容错误、涉密信息无法在入库前拦截，客户答案质量不可控 |
| P2：敏感/争议话题一刀切         | 移动客户 | 涉及投诉、资费、政策争议的提问，AI 直答存在合规与舆情风险，无兜底机制      |
| P3：开发文档会过时、答案无反馈闭环    | 厂商   | 工程师检索到过期/错误片段无处反馈，错误信息长期残留，影响开发效率         |
| P4：HITL 能力闲置          | 双方   | 现有 HITL 仅用于写库审批，使用频率低；未能覆盖内容生产与答案质量两类高频场景 |

## 3. 需求总览

| 编号  | 需求             | 侧    | 一句话价值                               | 优先级 | 复用程度            |
| --- | -------------- | ---- | ----------------------------------- | --- | --------------- |
| R1  | 知识库文档入库质量审核    | 厂商   | 入库前由管理员对 AI 处理结果把关，保障客户可见的内容质量与涉密安全 | P0  | 高（审批卡片+决策接口全复用） |
| R2  | 敏感/高风险回答复核与转人工 | 移动客户 | 敏感问题回答前人工复核/转人工，合规兜底兼客户体验保底         | P0  | 高（复用中断+恢复）      |
| R3  | 开发文档答案反馈纠错采纳   | 厂商   | 工程师对检索答案反馈"无用/纠错"，闭环到文档修订，防过时残留     | P1  | 中（复用审批卡片）       |

> 建议交付顺序：R1 → R2 → R3。R1 与 R3 均可独立上线；R2 依赖意图路由与敏感识别。

## 4. 需求一：知识库文档入库质量审核 HITL

### 4.1 用户故事

- 作为知识库管理员（厂商内部），当有新文档上传时，我希望 AI 自动完成解析、清洗、分块、摘要与标签生成，并在**向量入库前**由我确认或修订，以便过滤质量不合格或涉密内容后再面对客户；
- 作为管理员，我希望在审核卡片上直接看到「内容预览 / 分块分布 / 自动摘要 / 建议标签 / 质量检测结果」，并支持 **通过 / 修改后通过 / 打回 / 拒绝**。

### 4.2 触发条件

- 上传文档并进入入库流程（现有 `POST /file/process` + `save_embedding` 链路前端化）；
- AI 预处理完成后、执行向量化（`save_to_vectors`）与语义缓存失效**之前**。

### 4.3 流程（含 HITL 门）

```
用户上传文档 → AI 解析/清洗/分块/摘要/标签/质量扫描（同步完成）
        │
        ▼
HITL 门：生成"入库审核单" + SSE 推送审核卡片（status=pending）
        │
        ├─ 通过 ──────────────► 写入元数据/标签 → 向量化 → 缓存失效 → 发布完成
        ├─ 修改后通过 ─────────► 管理员修订摘要/标签 → 同上
        ├─ 打回 ──────────────► 标记 reason，文档回到"待修正"，通知上传人，不入库
        └─ 拒绝 ──────────────► 文档废弃，不更新知识库
```

### 4.4 审核卡片重点展示（复用审批卡片六区块）

| 区块  | 内容                                                      | 来源       |
| --- | ------------------------------------------------------- | -------- |
| 头部  | 操作类型=「文档入库」、目标=文件名、状态角标                                 | 系统       |
| 明细  | 内容预览（前 N 字符/首屏）、分块数、自动摘要、建议标签、质量检测结果（乱码/空块/重复率/涉密关键词命中） | AI 预处理输出 |
| 上下文 | 上传人、上传时间、文件类型/大小                                        | 系统       |
| 操作  | 通过 / 修改后通过（可编辑摘要与标签）/ 打回 / 拒绝 + 意见                      | 管理员      |
| 回显  | 审核人 / 审核时间 / 意见                                         | 系统       |
| 提示  | 未审核期间文档保持「未发布」状态，不影响存量检索                                | 系统       |

### 4.5 状态机

```
pending ──通过──► approved ──► 向量化发布 ──► published（终态）
   │    ──修改后通过─► approved(修订) ──► 同上
   │    ──打回──► returned（附 reason，可重新提交）
   │    ──拒绝──► rejected（终态，数据废弃）
```

### 4.6 业务规则

1. **默认不发布**：扫描质量为「通过」仅是 AI 建议，必须经管理员确认才入库（白名单优秀场景可配置免审）；
2. **涉密红线**：质量扫描命中涉密关键词（密码/工号/内网地址清单等）时**强制人工审核**，不可配置免审；
3. **幂等**：审核单仅 pending → 终态单向流转，重复决策被拦截；
4. **审计**：摘要/标签修订差异、决策意见全部落库，供追溯。

### 4.7 验收标准

- [ ] 上传文档后出现入库审核卡片，且此时知识库检索结果**不包含新文档**；
- [ ] 四种决策均可达，打回/拒绝附意见且通知上传人；
- [ ] 通过后向量化与语义缓存失效正确执行，检索可命中新文档；
- [ ] 涉密关键词命中时强制审核，免审配置不生效；
- [ ] 刷新页面后可经「会话审批列表」重建审核卡片。

## 5. 需求二：敏感/高风险回答人工复核与转人工 HITL

### 5.1 用户故事

- 作为移动客户，当我的提问涉及投诉、资费争议或政策边界时，我希望回答经过专业人员确认，而不是让 AI 直接给出可能不准确的结论；
- 作为客服管理员，当 AI 对高风险问题的置信度不足时，我希望系统自动进入**复核或转人工**，避免错误答复引发客诉。

### 5.2 触发条件（判定规则，符合任一即触发）

| 规则     | 说明                                                        |
| ------ | --------------------------------------------------------- |
| 敏感话题命中 | 意图路由 / 检索上下文命中配置的敏感清单（投诉、资费、携转、政策争议、法律等）                  |
| 低置信度   | 知识库检索无有效命中或意图置信度 < 阈值（复用现有 CONFIDENCE_THRESHOLD 机制，阈值可配置） |
| 规则白名单  | 命中即强制复核的强敏感关键词（不可跳过）                                      |

### 5.3 两种模式

| 模式       | 行为                                                     | 适用        |
| -------- | ------------------------------------------------------ | --------- |
| 1. 复核后发送 | AI 先生成**预答复**并推送「等待复核」卡片，复核人通过 → 正式发送；驳回 → 转人工应答并附复核意见 | 高价值/争议性问题 |
| 2. 直接转人工 | 不展示预答复，直接通知「已为您转接人工」并生成人工工单                            | 强敏感/紧急场景  |

> 建议：初版实现**模式 2（转人工）**，控制复杂度；模式 1（复核后发送）纳入二期。

### 5.4 转人工流程

```
客户提问 → 敏感/低置信判定 → HITL: 生成转人工记录 + 前置提示"已转人工，请稍候"
        │
        ├─ 人工接入 ──► 客服在对话窗口接手，完成服务
        └─ 超时未接入（可配置）──► 兜底发送通用安抚话术 + 工单编号
```

### 5.5 审批/转人工卡片说明

| 区块  | 内容                                  |
| --- | ----------------------------------- |
| 头部  | 操作类型=「转人工」、目标=会话、状态角标（已转人工/接入中/已接入） |
| 明细  | 客户原问题、AI 初审结论（预答复/置信度/命中的敏感规则）      |
| 上下文 | 会话发起人、历史轮次摘要（脱敏）                    |
| 操作  | 客服端「开始接待 / 结束接待」；客户侧无按钮仅提示          |
| 提示  | 转人工等待超时说明                           |

### 5.6 状态机（转人工单）

```
created(待接入) ──客服接受──► in_service(接入中) ──客服结束──► closed(已结束)
   └─超时/放弃──► timeout(兜底话术已发送)
```

### 5.7 业务规则

1. **强敏感规则优先**：命中白名单关键词忽略低置信逻辑，直接转人工；
2. **权限**：仅具备客服角色（可配置用户组）可接受转人工单；客户不可见内部字段；
3. **保底话术**：超时/失败必须有兜底文本，不允许静默失败；
4. **审计**：转人工触发规则、接入人、开始/结束时间、兜底情况全记录。

### 5.8 验收标准

- [ ] 敏感话题命中后不再输出 AI 直答，展示「已转人工」提示；
- [ ] 客服可接受/结束转人工单，会话转移至人工，AI 不干预；
- [ ] 超时触发兜底话术与工单编号；
- [ ] 强敏感关键词（配置清单）不被置信度兜底绕过；
- [ ] 转人工全过程可审计（触发依据、接入人、时长）。

## 6. 需求三：开发文档答案反馈纠错采纳闭环 HITL

### 6.1 用户故事

- 作为厂商工程师，当我检索开发文档得到答案时，我希望一键反馈「回答没用/有错误」并填写偏差内容，让文档作者及时修订，避免错误长期残留；
- 作为文档维护人，我希望能集中看到文档被反馈的问题，并**逐个确认**是否修订/驳回，保证文档库质量随使用持续提升。

### 6.2 触发条件

- 知识库问答（knowledge_base 分支）完成后，答案卡片提供「有用 / 无用+纠错」反馈入口；
- 用户选择「无用」并填写纠错内容 → 生成**纠错反馈单**并进入 HITL 审核。

### 6.3 流程

```
工程师检索答案 → 反馈"无用 + 纠错内容" → 生成纠错反馈单（关联文档/答案快照）
        │
        ▼
HITL 门：推送审核卡片给文档维护人（status=pending）
        │
        ├─ 采纳 ──────► 标记文档"待修订"，生成修订任务（责任人可接） → 修订后重新入库
        ├─ 驳回 ──────► 附驳回理由，反馈给反馈人
        └─ 归档 ──────► 确认已过期 → 下线该文档（从检索移除 / 标记废弃）
```

### 6.4 卡片重点展示

| 区块  | 内容                            |
| --- | ----------------------------- |
| 头部  | 操作类型=「文档纠错」、目标=文档名/片段 ID、状态角标 |
| 明细  | 原答案（快照）、工程师反馈的纠错内容、命中文档片段预览   |
| 上下文 | 反馈人、反馈时间、所属文档路径               |
| 操作  | 采纳（+指派修订人）/ 驳回（+理由）/ 归档下线     |
| 提示  | 未处理期间原文档继续可检索，但标记"有反馈待处理"     |

### 6.5 状态机

```
pending ──采纳──► accepted ──修订完成──► revised（重新入库）
   │    ──驳回──► rejected（附理由，回执反馈人）
   │    ──归档──► archived（下线文档）
```

### 6.6 业务规则

1. **答案快照**：反馈单必须固化当时的答案与引用片段，避免文档修订后追溯失真；
2. **关联**：反馈单关联文档 ID 与 chunk ID，支持定位到具体片段；
3. **闭环统计**：反馈量 / 处理率 / 平均处理时长作为知识库质量看板指标；
4. **防滥用**：同一用户对同一答案的重复"无用"反馈去重合并。

### 6.7 验收标准

- [ ] 知识库答案卡片提供「有用/无用」反馈入口，可填写纠错内容；
- [ ] 反馈生成纠错反馈单，文档维护人可收到并经卡片处理；
- [ ] 采纳后生成修订任务，修订重新入库后原反馈单关闭；
- [ ] 归档下线后文档不再出现在检索结果；
- [ ] 反馈全链路可审计、可统计。

## 7. 复用与扩展现有 HITL 基础设施

三个需求均**不引入新的中断原语**，全部复用现有能力：

| 现有组件               | 复用方式                                                                                      | 扩展点                       |
| ------------------ | ----------------------------------------------------------------------------------------- | ------------------------- |
| approval_request 表 | 作为通用「人工介入单」，新增 `biz_type` 字段区分 write_approval / doc_review / tech_handover / doc_feedback | 字段新增（biz_type、payload 扩展） |
| SSE 事件             | approval_required / approval_decided 协议不变，卡片载荷按 biz_type 差异化渲染                            | 前端卡片按类型分发子组件              |
| 决策接口               | `POST /api/approval/{id}/decision` 语义扩展：决策枚举按 biz_type 扩展（approve/reject + review 特有动作）   | 决策枚举按需扩展                  |
| MySQL 检查点          | 需要挂起恢复的流程（如 R2 复核后发送）复用 thread_id 恢复                                                      | 无                         |
| 审批等待/心跳/超时         | 复用 wait_for_final + ping 机制                                                               | 超时阈值按需求可配置                |
| 前端 ApprovalCard    | 六区块骨架复用                                                                                   | 明细区块按 biz_type 渲染不同内容     |

> 建议：将现有「写操作审批」与三个新需求统称为 **Agent 人工介入中心（HITL Collection）**，同一套卡片、接口、状态机承载多类场景。

## 8. 数据与接口设计

### 8.1 审批/介入单表扩展（approval_request）

| 字段              | 现有                   | 扩展                                                         |
| --------------- | -------------------- | ---------------------------------------------------------- |
| biz_type        | write_approval       | write_approval / doc_review / tech_handover / doc_feedback |
| approval_type   | update/delete/insert | 增加 doc_publish / handover / doc_fix                        |
| tool_params     | 写操作参数                | 携带审核核心载荷（文档摘要/质量报告/原答案快照等）                                 |
| requester_id    | 发起人                  | 文档入库=上传人；转人工=customer；纠错=工程师                               |
| approved_by     | 审批人                  | 审核人/接入客服/文档维护人                                             |
| decision_reason | 审批意见                 | 打回/驳回/修订指派理由复用                                             |

### 8.2 接口清单（在现有基础上扩展）

| 方法   | 路径                                       | 说明                     |
| ---- | ---------------------------------------- | ---------------------- |
| POST | `/api/approval/{id}/decision`            | 扩展：按 biz_type 透传对应决策枚举 |
| POST | `/api/kb-docs`                           | 新文档入库（预处理 + 审核门触发）     |
| POST | `/api/kb-docs/{doc_id}/publish`          | 审核通过后发布（向量化+缓存失效，后台任务） |
| POST | `/api/handover/{id}/accept` / `finish`   | 转人工单受理/结束              |
| POST | `/api/feedback`                          | 答案有用性反馈 + 纠错内容提交       |
| GET  | `/api/approval?conversation_id&biz_type` | 会话审批列表支持按类型过滤          |

## 9. 风险与注意事项

1. **审核时效**：文档入库与转人工均有时效诉求，需配置合理的等待超时；入库建议默认「异步发布」（审核通过后台执行，不阻塞上传人）；转人工必须有兜底话术；
2. **免审与安全平衡**：白名单免审仅限「低风险文档类型」，涉密关键词命中必须强制审核，不可配置绕过（与 §11 安全设计一致）；
3. **误判转人工**：敏感判定过严会拉高人工成本，初期建议"敏感命中仅标记、仅强敏感才转人工"，先观测再收紧；
4. **反馈噪音（R3）**：防止恶意/重复反馈，需去重与频率限制；
5. **与现有写操作审批并存**：biz_type 归一后需回归验证写审批链路不受影响；
6. **依赖要求**：R2 依赖意图路由与敏感词配置（prompt_storage 扩展）；R1/R3 依赖文档块元数据（doc_id/chunk 关联，现有能力已具备）。
